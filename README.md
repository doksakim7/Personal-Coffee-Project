# ☕ 커피 주문 시스템

## 📌 프로젝트 개요

본 시스템은 다수의 서버 환경에서도 안정적으로 동작하는 커피 주문 시스템을 목표로 한다.  
특히 **동시성 제어**, **데이터 일관성**, **확장성**을 고려하여 설계하였다.

---

## 1. 요구사항 분석 및 비즈니스 정책

### 🔍 주요 문제 정의

1. **포인트 차감 시 동시성 문제**
   - 동일 사용자의 다중 요청으로 포인트가 중복 차감될 수 있음
   - 최악의 경우 포인트가 음수가 되는 문제 발생

2. **인기 메뉴 집계 성능 문제**
   - DB 기반 실시간 집계 시 성능 저하 발생

3. **주문 이벤트 비동기 처리 필요**
   - 주문 데이터를 외부 시스템(로그/분석)으로 전달 필요

---

### 🛠 해결 전략

- Redis 분산락을 통한 동시성 제어
- Redis ZSet을 활용한 인기 메뉴 집계
- Kafka를 통한 주문 이벤트 비동기 처리

---

### 📌 비즈니스 정책

본 시스템은 포인트 기반 결제와 동시성 제어를 핵심으로 설계되었으며,
다음과 같은 비즈니스 정책을 따른다.

---

#### 🔐 인증/인가
- 별도의 관리자 기능은 제공하지 않는다.
- 모든 사용자는 동일한 권한을 가진다.

---

#### ☕ 메뉴 정책
- 메뉴 재고는 무한으로 가정한다.
- 메뉴 데이터는 더미 데이터로 관리한다.
- 메뉴는 상태(status)를 통해 관리된다.
  - ACTIVE: 주문 가능
  - INACTIVE: 숨김
  - SOLD_OUT: 일시 품절
- 주문 요청 시 메뉴 상태가 ACTIVE인지 검증한다.

---

#### 💰 포인트 정책
- 결제는 포인트 기반으로만 수행된다.
- 충전 금액은 10,000원 이상이며 5,000원 단위로 제한한다.
- 포인트는 음수가 될 수 없다.
- 주문 취소 시 차감된 포인트는 환불 처리된다.
- 모든 포인트 변경 내역은 POINT_HISTORY에 기록된다.
- 포인트 차감은 동시성 제어 대상이다.

---

#### 🛒 주문 처리 정책

##### 1. 주문 전 검증
- 사용자 포인트가 결제 금액 이상인지 확인한다.
- 메뉴 상태가 ACTIVE인지 확인한다.
- 요청 파라미터(수량, 메뉴 ID 등)의 유효성을 검증한다.

##### 2. 주문 상태 처리
- 주문 생성 시 초기 상태는 PENDING이다.
- 결제 성공 시 ORDERED 상태로 변경된다.
- 결제 실패 또는 예외 발생 시 CANCELED 상태로 변경된다.
- 주문 취소 시 ORDER 상태를 CANCELED로 변경하고, 차감된 포인트를 환불하며 POINT_HISTORY에 REFUND 이력을 기록한다.

##### 3. 실패 처리
- 포인트 차감 실패 시 주문을 생성하지 않는다.
- 주문 생성 실패 시 차감된 포인트는 롤백된다.
- 예외 발생 시 전체 트랜잭션을 롤백한다.

---

#### 📊 인기 메뉴 집계 정책
- 주문이 ORDERED 상태로 확정된 경우에만 집계에 반영한다.
- 취소(CANCELED)된 주문은 집계에서 제외한다.
- ZSet key는 "popular:menus"로 관리하며, member는 menuId, score는 주문 횟수로 증가시키는 방식으로 집계한다.

---

#### 🗑 데이터 삭제 정책 (Soft Delete)
- 모든 주요 엔티티는 물리 삭제 대신 소프트 딜리트를 적용한다.
- 삭제 시 deleted_at 컬럼에 삭제 시각을 기록한다.
- deleted_at이 NULL인 데이터만 유효한 데이터로 간주한다.

##### 적용 대상
- USER
- MENU
- ORDER

##### 정책
- 삭제된 데이터는 조회 대상에서 제외한다.
- 과거 주문 및 포인트 이력 데이터의 무결성을 유지하기 위해 물리 삭제는 수행하지 않는다.

```text
   ↓

   ↓

   ↓
[Consumer (로그/분석)]
```

---

### 🔥 주문 처리 흐름

주문 처리 흐름은 전체 요청의 실행 순서를 설명한다.

1. Client → 주문 요청
2. Redis 분산락 획득 (userId 기준)
3. 포인트 조회 
4. 포인트 검증 
5. 포인트 차감(POINT_HISTORY에 USE 이력 기록)
6. 주문 생성 (PENDING 상태)
7. 주문 상태 변경 (PENDING → ORDERED)
8. Redis ZSet 증가 (인기 메뉴 집계, ORDERED 기준)
9. Kafka 이벤트 전송 (트랜잭션 커밋 이후 비동기 처리)
10. 락 해제

---

### ⚙️ 기술 선택

#### ✅ Redis
- Redis 분산락을 활용하여 멀티 인스턴스 환경에서 동시성 문제를 해결
- ZSet → 인기 메뉴 실시간 집계
- ZSet key는 "popular:menus"로 관리

#### ✅ Kafka
- 주문 처리와 데이터 수집을 분리하기 위해 사용
- 비동기 처리로 성능 저하 방지 및 확장성 확보
- Kafka 이벤트는 DB 트랜잭션 커밋 이후 비동기로 발행
- 이벤트 발행 실패에 대비하여 재시도 또는 로그 기반 재처리 전략을 적용

#### ✅ k6
- 동시 요청 테스트
- Race Condition 검증

## 4. 동시성 및 핵심 로직 설계

### ⚠️ 동시성 문제 정의

동일 사용자가 동시에 여러 주문 요청을 보낼 경우,  
포인트 차감 과정에서 race condition이 발생할 수 있다.

이로 인해 포인트가 중복 차감되거나 음수가 되는 문제가 발생할 수 있다.

---

### 🛠 해결 전략

Redis 분산락은 userId 기준으로 적용하여 동일 사용자에 대한 동시 요청을 직렬화하고,
락은 일정 시간 후 자동 해제되도록 TTL을 설정하여 장애 상황에서도 락이 유지되지 않도록 한다.

---

### 🔄 트랜잭션 처리

포인트 차감과 주문 생성은 하나의 트랜잭션으로 처리하여  
데이터 일관성을 보장한다.

즉, 하나라도 실패할 경우 전체 작업은 롤백된다.

---

### 🔁 주문 처리 로직

주문 처리 로직은 트랜잭션 경계와 내부 처리 방식을 정의한다.    
그리고 다음과 같은 트랜잭션 단위로 구성된다.

- 포인트 차감과 주문 생성은 하나의 트랜잭션으로 처리된다.
- Redis 락은 트랜잭션 외부에서 획득하여 동시성을 제어한다.
- Kafka 이벤트는 트랜잭션 커밋 이후 비동기로 처리된다.

---

### ⚠️ 예외 처리 전략

- 락 획득 실패 시 일정 횟수 재시도 후 실패 처리
- Kafka 전송 실패 시 로그 기록 및 재처리 전략 적용

## 6. ERD 및 데이터 설계

본 ERD는 주문 흐름(CART → ORDER → ORDER_ITEM)과 포인트 이력 관리를 중심으로 설계하였다.

<img width="1118" height="768" alt="커피 프로젝트 ERD" src="https://github.com/user-attachments/assets/514a5736-7db0-43ac-88e1-f5a955d23f7b" />

### 데이터 설계 정책
- total_price는 ORDER_ITEM의 (price × quantity)의 합으로 계산한다.
- 주문 생성 후 CART_ITEM은 초기화된다.
- amount는 충전(+), 사용(-), 환불(+)으로 관리한다.
- 이미지는 외부 스토리지(S3 등)에 저장하고 URL만 관리한다.
- 모든 조회는 Soft Delete 정책에 따라 deleted_at IS NULL 조건을 기본으로 한다.
- USER.point는 조회 성능을 위한 캐시 역할을 하며, 실제 정합성은 POINT_HISTORY를 기준으로 관리한다.

### 주문 상태 흐름
PENDING → ORDERED (결제 성공)
PENDING → CANCELED (결제 실패/취소)
ORDERED → CANCELED (환불 시)

### 장바구니 → 주문 변환 흐름
CART → ORDER 생성 시
CART_ITEM → ORDER_ITEM으로 복사

### 성능 최적화
- order_id, menu_id 컬럼에 인덱스를 적용하여 주문 조회 및 통계 조회 성능을 향상시킨다.

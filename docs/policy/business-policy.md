# 📌 비즈니스 정책

본 시스템은 포인트 기반 결제 시스템에서 발생할 수 있는 동시성 문제를 해결하는 데 초점을 맞추었으며,
다수의 서버 환경에서도 안정적으로 동작하도록 설계하였다.

---

## 🧠 설계 의도
- 포인트 차감은 데이터 정합성이 가장 중요한 영역이므로 Redis 분산락과 트랜잭션을 함께 사용하여 동시성 문제를 해결한다.
- 인기 메뉴는 조회 성능이 중요하기 때문에 Redis ZSet을 활용하여 DB 부하를 줄인다.
- 주문 이벤트는 Kafka를 통해 비동기 처리하여 시스템 간 결합도를 낮추고 확장성을 확보한다.
- Kafka 전송 실패 시 로그 기록 및 재처리 전략을 적용한다.

---

## 🔐 인증/인가
- 별도의 관리자 기능은 제공하지 않는다.
- 모든 사용자는 동일한 권한을 가진다.

---

## ☕ 메뉴 정책
- 메뉴 재고는 무한으로 가정한다.
- 메뉴 데이터는 더미 데이터로 관리한다.
- 메뉴는 상태(status)를 통해 관리된다.
    - `AVAILABLE`: 주문 가능
    - `INACTIVE`: 숨김
    - `SOLD_OUT`: 일시 품절
- 주문 요청 시 메뉴 상태가 `AVAILABLE`인지 검증한다.
- 조회 시 `AVAILABLE`, `SOLD_OUT` 상태의 메뉴만 노출되며, `INACTIVE` 상태는 제외된다.

---

## 💰 포인트 정책
- 결제는 포인트 기반으로만 수행된다.
- 충전 금액은 10,000원 이상이며 5,000원 단위로 제한한다.
- 충전 금액은 최대 2,000,000원 까지 가능하다.
- 포인트는 음수가 될 수 없다.
- 포인트는 정수 단위로 관리되며 소수점은 허용하지 않는다.
- 포인트 충전은 현금 → 포인트로 변환된다.
- 포인트 환전은 포인트 → 현금으로 변환된다.
- 환전 요청 시 포인트가 충분한지 검증한다.
- 환전 실패 시 포인트는 차감되지 않는다.
- `ORDERED` 상태에서 취소 시에만 포인트를 복구한다.
- `PENDING` 상태 취소 시 포인트 변화는 없다.
- 모든 포인트 변경 내역은 POINT_HISTORY에 기록된다.
- `USER.point`는 현재 포인트 잔액의 기준 값이며, `POINT_HISTORY`는 포인트 변경 이력을 기록하는 로그로 사용된다.
- 모든 포인트 변경은 두 테이블에 동시에 반영된다.
- 포인트 차감은 동일 사용자(userId) 기준으로 동시성 제어를 수행한다.
- 포인트 변경(`USER.point, POINT_HISTORY`)은 항상 동일 트랜잭션 내에서 처리된다.

---

## 📌 장바구니 정책
- 장바구니는 사용자별로 1개만 존재한다.
- 동일 메뉴를 추가할 경우 수량이 증가한다.
- 메뉴 상태가 `AVAILABLE`인 경우에만 추가 가능하다.
- 수량은 1 이상이어야 한다.
- 장바구니는 주문 결제 성공(`ORDERED`) 시 초기화된다.
- 장바구니는 주문 시점의 스냅샷 기준으로 처리된다.
- 동시 요청으로 인한 중복 주문은 서버에서 제어한다.
- 장바구니 데이터는 임시 데이터로 간주되며, 삭제 시 물리 삭제(Hard Delete)를 수행한다.
- 장바구니 → 주문 전환 시 `CART_ITEM`은 `ORDER_ITEM`으로 복사된다.

## 🛒 주문 처리 정책

### 1. 주문 생성 전 검증
- 주문 생성 단계에서는 포인트를 검증하지 않으며, 포인트 검증은 결제 단계에서 수행한다.
- 주문 생성 전에 메뉴 상태가 `AVAILABLE`인지 검증한다.
- 요청 파라미터(수량, 메뉴 ID 등)의 유효성을 검증한다.
- 동일 사용자 기준 `PENDING` 상태 주문은 1개만 허용하며, 미결제 주문이 존재하는 경우 새로운 주문 생성은 불가하다.

### 2. 결제 전 검증
- 사용자 포인트가 결제 금액 이상인지 확인한다.
- 결제 시점에도 메뉴 상태를 재검증하여, 주문 생성 이후 상태 변경(`INACTIVE` 등)에 대응한다.
- 요청 파라미터(수량, 메뉴 ID 등)의 유효성을 검증한다.

### 3. 주문 상태 처리
- 주문 생성 시 초기 상태는 `PENDING`이다.
- 결제 성공 시 `ORDERED` 상태로 변경된다.
- 비즈니스 실패(포인트 부족 등) 시 `CANCELED_BY_SYSTEM` 상태로 변경된다.
- 주문 취소 시 주문 상태(`OrderStatus`)를 `CANCELED_BY_USER`로 변경하고, 차감된 포인트를 복구하며 `POINT_HISTORY`에 `REFUND` 이력을 기록한다.
- 주문 취소 상태는 다음 두 가지로 나뉜다:
  1) 결제 실패로 인한 취소(`CANCELED_BY_SYSTEM`)
  2) 사용자 요청에 의한 주문 취소(`CANCELED_BY_USER`)

### 4. 실패 처리
- 비즈니스 실패(포인트 부족 등) 발생 시 주문 상태를 `CANCELED_BY_SYSTEM`으로 변경한다. (단, 이는 정상적인 비즈니스 흐름이며 트랜잭션 내에서 커밋된다)
- 시스템 예외 발생 시 트랜잭션 롤백으로 인해 상태 변경이 반영되지 않는다. (`PENDING` 유지)

### 5. 동시성 처리
- 주문 처리 시 Redis 분산락을 사용하여 동일 사용자 요청을 직렬화한다.
- 분산락 → 검증 → 주문 상태 변경 준비 → 포인트 차감 + 상태 변경 (같은 트랜잭션, `PENDING` → `ORDERED`) 순으로 처리하여 데이터 정합성을 보장한다.

### 6. 멱등성 처리
- 주문 생성 API는 `Idempotency-Key`를 기반으로 동일 요청을 식별하여 중복 결제 및 중복 주문 생성을 방지한다.
- 동일한 요청에 대해 중복 결제가 발생하지 않도록 서버에서 제어한다.

---

## 📊 인기 메뉴 집계 정책
- 주문이 `ORDERED` 상태로 확정된 경우에만 집계에 반영한다.
- 취소(`CANCELED_BY_USER`, `CANCELED_BY_SYSTEM`)된 주문은 집계에서 제외한다.
- ZSet key는 "popular:menus"로 관리하며, member는 menuId, score는 주문 횟수로 증가시키는 방식으로 집계한다.
- 인기 메뉴는 Redis ZSet 기반으로 처리되며, 주문 이벤트 발생 시 즉시 반영되지만 분산 환경 특성상 최종 일관성(eventual consistency)을 따른다.

---

## 🗑 데이터 삭제 정책 (Soft Delete)
- 모든 주요 엔티티는 물리 삭제 대신 소프트 딜리트를 적용한다.
- 단, `CART`, `CART_ITEM`은 Soft Delete 대상에서 제외
- 삭제 시 deleted_at 컬럼에 삭제 시각을 기록한다.
- deleted_at이 NULL인 데이터만 유효한 데이터로 간주한다.
- 삭제된 데이터는 조회 대상에서 제외한다.
- 과거 주문 및 포인트 이력 데이터의 무결성을 유지하기 위해 물리 삭제는 수행하지 않는다.


### Soft Delete 적용 대상
- `USER`
- `MENU`
- `ORDERS`
